结论：用户已明确实际用途为复制到 WPS / Word 后继续编辑公式，因此该项目的 OMML 结构保留思路与目标相关。它不是现成的 LaTeX 转 TXT 引擎，也未提供跨应用剪贴板实现。当前采用已有 Pandoc 独立实现 MathML / OMML 复制，不移植其无明确许可证的解析器。

2026-10-20 落地结果：桌面版 0.1.4 同时提供 Word 的 MathML 和 WPS 的原生 DOCX 剪贴板表示。本机 Word 16.0.20430.20092、WPS 12.1.0.28043 各通过分式、根号、上下标、带上下界大析取、矩阵、混排文字粘贴检查，均为可编辑公式对象。转换时不启动 Office、不联网。详细使用方式见 `可编辑公式复制说明-0.1.4.md`。

## 实际功能与我们的需求

项目主流程为：浏览器本地打开 DOCX → 找出文字中的 LaTeX 候选 → 自定义解析器生成公式节点 → 输出 Word/WPS 可编辑的 Office Math（OMML）→ 下载 DOCX 和转换报告。

| 需求 | 此项目的适用程度 |
|---|---|
| LaTeX 源码转可复制 TXT | 可参考解析部分，但需要新增独立纯文本输出器和语义保护 |
| LaTeX 源码转 Word/WPS 原生公式 | 这是项目的主要用途，仍需检查支持范围 |
| 公式图片转文本 | 不包含图片公式识别，不能替代现有 OCR 模型 |
| 手机本机处理 | 浏览器本地处理思路适用，但 TypeScript/浏览器接口不能直接放进当前 Python 或 Dart 模块 |

核心文件：

- `webapp/app/docx-converter.ts`：公式候选发现、解析器、OMML 写出、DOCX XML 替换。
- `webapp/standalone-entry.ts`：离线网页入口。
- `webapp/README.md`：声称的支持范围与处理原则。

## 值得借鉴的做法

1. 先把公式表示为结构节点，再输出目标格式。节点包含分式、根号及根次、上下标、重音、带上下界的大运算符和矩阵，避免仅靠全局字符串替换。
2. 同时处理明确的公式标记、独立公式和部分没有标记的公式候选。
3. 保留公式所在段落、原文、位置和告警，产生逐公式转换报告，方便用户复核。
4. 能定位正文、表格及相关 Word 文档部件中的文字，对以后增加 Word 原生公式导出有参考价值。

其中“候选置信度”来自启发式规则，不是数学语义正确率，不能把“高”当成公式内容已经验证正确。

## 源码与隔离实测发现的限制

只提取并测试了已阅读的解析器部分，没有安装依赖、运行项目安装脚本、启动网页或将源码接入现有程序。解析器测试在无网络/文件 API 注入的独立 JavaScript 上下文中运行；未验证完整 DOCX 在 Word/WPS 中的显示效果。

共检查 10 类输入：

| 用例 | 实际观察 |
|---|---|
| 嵌套分式 | 正确生成分子/分母的嵌套节点，值得参考 |
| 三次根号 | 根次 `3` 单独保存在结构中 |
| `used[t]\iff\bigvee_{i=0}^{5}(slot[i]=t)` | `iff`、`bigvee` 都产生“暂不识别命令”警告，没有转成对应逻辑符号 |
| `vmatrix` 行列式 | 没有保留环境类型或竖线信息 |
| `pmatrix` 普通矩阵 | 与上面的行列式生成相同节点；对应写出逻辑对非 cases 环境输出裸矩阵 |
| `\mathbf{x}+x` | 粗体部分仅作为普通 group，写出时没有保留粗体数学区分 |
| `\text{a b}` | 文本内部的空格在解析时被跳过 |
| 不完整的 `\frac{x}` | 分母为空，但警告列表也为空；不能仅靠现有告警判断转换安全 |
| `x^12` | 把 `12` 整体放入上标；严格 LaTeX 中未加花括号时通常只取一个字符，因此需明确是否做输入修复 |
| 全称、存在量词组合 | 对 `forall`、`exists`、`to` 等可生成对应文字符号节点 |

此外，`convertDocx` 在节点非空时继续生成并替换公式，并未统一要求警告为空。不支持的命令可能仍进入输出，最终记录为“已转换”并附警告。若参考报告机制，应另加“有语义风险时保留整段原文”的强制门槛。

这些问题说明：不能因为项目输出可编辑公式，就推断公式含义一定被完整保留。直接替换可能重新引入当前程序已经修过的问题。

## 与当前程序的衔接建议

当前桌面端 `factory/text.py` 已使用 pylatexenc 的语法节点，并加入分式分组、根次和复杂结构保留，不是单纯的正则替换。手机端 `mobile/lib/core/text_editing.dart` 仍有较多规则转换，统一结构化表示对手机端更有价值。

建议保留现有图片识别层，把源码转换与图片识别分开验证。在现有解析能力上统一公式结构，再按需输出：

```text
LaTeX 源码
   ↓
公式结构 + 原始片段 + 告警
   ├─ 可读纯文本（括号、运算符和上下标范围必须明确）
   ├─ LaTeX 原文回退（不能可靠表达的结构）
   └─ Word/WPS 可编辑公式（如果以后需要）
```

输出前继续验证之前的逻辑公式、分式后接平方/阶乘、根次、向量、行列式、增广矩阵、分段函数及未知命令。源码转换质量和图片识别准确率应分别报告；换一个源码解析器不能修复 OCR 把 0 看成 a 的问题。
